# Spec: Детерминированная сортировка товаров по характеристикам через `sort_key`

## 1. Контекст и проблема

В каталоге сайта и в выгрузках (Excel, API) у товаров отсутствует физическое поле порядкового номера (`ordering`).
Исторически порядок товаров на страницах категорий строился динамически в оперативной памяти Node.js (`products.sort(...)` в `server/api/getData/category/[c_alias].js`):
1. Выбирались группы характеристик из `usePrpsGroupsMap(productsCatId)`.
2. Группы сортировались по `a.ordering - b.ordering` (Тип: 10, Система отсчета: 20, Диапазон: 30, Размерность: 40, Точность: 50, Класс: 60, Особенности: 70, Производитель: 80, Упаковка: 90).
3. Внутри групп значения сортировались по `i_properties.ordering`.
4. В памяти запускался N-мерный цикл сравнения товаров по вхождению их параметров в упорядоченные группы фильтра.

### Проблемы текущего подхода:
- **Отсутствие сортировки в БД:** Невозможно сделать эффективную пагинацию (`LIMIT / OFFSET`), сортировку в SQL и в выгрузках.
- **Хаос в Excel:** В `server/api/excel/get-products.get.js` товары отдаются по `ORDER BY p.id ASC`, из-за чего в таблице `prices&quantity.xlsm` товары идут вразнобой по ID добавления, а не по логическому каталогу.
- **Дублирование тяжелой логики:** В 4 разных местах кодовой базы написан один и тот же цикл `products.sort(...)`.
- **Производительность:** На каждый запрос категории сервер тратит процессорное время на повторную сортировку одних и тех же массивов.

## 2. Архитектурное решение: `sort_key` (Composite Lexicographical Key)

В таблицу `i_products` добавляется колонка `sort_key VARCHAR(64)`.
Сортировочный ключ вычисляется для каждого товара детерминированно на основе его характеристик по ГОСТ-каталогу с фиксированной шириной блоков (4 цифры с ведущими нулями).

### Формат ключа:
```text
[P1_type]_[P2_system]_[P3_range]_[P4_size]_[P5_accuracy]_[P6_class]_[P7_feature]_[P0_brand]_[P8_pack]_[ID]
```

- **Разделитель:** `_` (символ подчеркивания, ASCII 95).
- **Длина каждого блока свойства:** 4 символа с заполнением нулями слева (`LPAD(order, 4, '0')`).
- **Если свойство не задано (0 или NULL):** подставляется `'9999'` (товары без данного свойства идут в конец соответствующей группы).
- **Tie-Breaker (разрешение споров):** в конец ключа добавляется `LPAD(p.id, 6, '0')`. При абсолютно одинаковых характеристиках гарантируется стабильный детерминированный порядок по ID без зависимости от цен и остатков.

### Пример:
Для микрометра МК (тип order=10), диапазон 0-25 (order=5), точность 0.01 (order=10), бренд ЧИЗ (order=1), ID 110005:
```text
0010_9999_0005_9999_0010_9999_9999_0001_9999_110005
```

## 3. Требования к реализации

### 3.1. Изменения схемы БД
1. Колонка `sort_key VARCHAR(64) NOT NULL DEFAULT ''` в таблице `i_products`.
2. Индекс `idx_cat_sort (category_id, sort_key)` для быстрого чтения страниц категорий.
3. Миграционный скрипт, вычисляющий и проставляющий `sort_key` для всех существующих товаров.

### 3.2. Серверная утилита генерации ключа
Модуль `server/utils/productSortKey.js`:
- Функция `buildProductSortKey(product, propsOrderingMap)`:
  - Принимает объект товара (`p1_type, p2_counting_system, ..., id`).
  - Принимает справочник весов `propsOrderingMap` (`Map<propId, ordering>`).
  - Возвращает нормализованную строку `sort_key`.
- Функция `recalculateProductsSortKey(productIds | categoryId)`:
  - Загружает свойства товаров, формирует `sort_key` и выполняет `UPDATE i_products SET sort_key = ...`.

### 3.3. Триггеры обновления `sort_key` при изменении характеристик
Поле `sort_key` обязано автоматически пересчитываться в следующих точках:
1. **Редактирование товара в админке:**
   - `server/api/admin/cms/products/updProds.js`: при обновлении `p0_brand`..`p8_pack`.
2. **Импорт товаров:**
   - `server/api/admin/dbImport/products.js`: при создании/обновлении товаров.
3. **Обновление свойств из админки:**
   - `server/api/admin/setProperties.js`: если изменяется `ordering` свойства в таблице `i_properties`, запускается пересчет `sort_key` для всех товаров, использующих данное свойство.

### 3.4. Рефакторинг существующих мест сортировки
Удаление устаревшей сортировки в памяти (`products.sort(...)`) и переход на SQL `ORDER BY sort_key ASC`:
1. `server/api/getData/category/[c_alias].js`:
   - В SQL-запросе: `ORDER BY sort_key ASC`.
   - Полное удаление ручного блока сортировки (строки 80–108).
2. `server/api/excel/get-products.get.js`:
   - В SQL-запросе: замена `ORDER BY p.id ASC` на `ORDER BY p.category_id ASC, p.sort_key ASC`.
   - В результате на листе Excel `prices` товары сразу структурированы по категориям и размерным рядам ГОСТ.
3. `server/api/ai/productsData/[c_alias].js`:
   - Удаление дублирующего блока сортировки (строки 211–255), чтение `ORDER BY sort_key ASC`.
4. `server/api/admin/cms/documentation/getProds.js`:
   - Удаление дублирующего блока сортировки (строки 83–93), чтение `ORDER BY sort_key ASC`.
5. `app/pages/admin/cms/products.vue`:
   - Очистка клиентской сортировки (строки 270–295) — список товаров категории приходит с сервера уже упорядоченным.

## 4. Критерии приемки (Definition of Done)
1. В таблице `i_products` присутствует колонка `sort_key` с индексом `(category_id, sort_key)`.
2. 100% опубликованных товаров имеют корректно рассчитанный `sort_key`.
3. Порядок товаров на странице категории идентичен каталожному ГОСТ-порядку без запуска `products.sort` в Node.js.
4. В Excel по методу `/get-products` товары выгружаются в правильном порядке категорий и параметров.
5. При смене любого свойства товара в админке `sort_key` обновляется автоматически.
6. При смене порядка `ordering` в `i_properties` зависимые товары обновляют свои ключи.
