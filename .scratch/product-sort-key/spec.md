# Spec: Детерминированная сортировка товаров по характеристикам через `sort_key`

## 1. Контекст и проблема

В каталоге сайта и в выгрузках (Excel, API) у товаров отсутствует физическое поле порядкового номера (`ordering`).
Исторически порядок товаров на страницах категорий строился динамически в оперативной памяти Node.js (`products.sort(...)` в `server/api/getData/category/[c_alias].js`):
1. Выбирались группы характеристик из `usePrpsGroupsMap(productsCatId)`.
2. Группы сортировались по `a.ordering - b.ordering` (Тип: 10, Система отсчета: 20, Диапазон: 30, Размерность: 40, Точность: 50, Класс: 60, Особенности: 70, Производитель: 80, Упаковка: 90).
3. Внутри групп значения сортировались по `i_properties.ordering`.
4. В памяти запускался N-мерный цикл сравнения товаров по вхождению их параметров в упорядоченные группы фильтра.

### Проблемы текущего подхода:
- **Отсутствие сортировки в БД:** Невозможно сделать эффективную пагинацию (`LIMIT / OFFSET`), сортировку в SQL и в выгрузках.
- **Хаос в Excel:** В `server/api/excel/get-products.get.js` товары отдаются по `ORDER BY p.id ASC`, из-за чего в таблице `prices&quantity.xlsm` товары идут вразнобой по ID добавления, а не по логическому каталогу.
- **Дублирование тяжелой логики:** В 4 разных местах кодовой базы написан один и тот же цикл `products.sort(...)`.
- **Производительность:** На каждый запрос категории сервер тратит процессорное время на повторную сортировку одних и тех же массивов.

## 2. Архитектурное решение: `sort_key` (Composite Lexicographical Key)

В таблицу `i_products` добавляется колонка `sort_key VARCHAR(64)`.
Сортировочный ключ вычисляется для каждого товара детерминированно как **внутрикатегорийный индекс** (intra-category) на основе его характеристик с фиксированной шириной блоков (4 цифры с ведущими нулями).
Для глобальных выгрузок (Excel) сортировка по категориям решается на уровне SQL: `JOIN i_categories c ON c.id = p.category_id ORDER BY c.ordering ASC, p.sort_key ASC`.

### Формат ключа:
Ключ всегда состоит строго из **10 блоков** (9 блоков характеристик + 1 блок ID):
```text
[B1]_[B2]_[B3]_[B4]_[B5]_[B6]_[B7]_[B8]_[B9]_[ID]
```

- **Разделитель:** `_` (символ подчеркивания, ASCII 95).
- **Длина каждого блока свойства:** строго 4 символа с заполнением нулями слева (`String(order).padStart(4, '0')`).
- **Последовательность блоков характеристик:** определяется динамически для категории товара (`product.category_id`) на основе `usePrpsGroupsMap(category_id)`:
  1. Активные группы (`!group.disabled`) сортируются по возрастанию `(group.sortOrdering ?? group.ordering)`. Это обеспечивает консистентность с фильтром по умолчанию, но позволяет точечно переопределять приоритет сортировки через `sortOrdering` (например, вынести Материал вперед для штангенциркулей).
  2. Отключенные группы (`group.disabled === true`, например `p8_pack`) помещаются в конец списка групп.
- **Значения блоков свойств:**
  - Если характеристика задана у товара и группа активна: `LPAD(i_properties.ordering, 4, '0')` (значения в базе 1..198).
  - Если характеристика не задана (0, null, undefined) ИЛИ группа помечена `disabled: true`: подставляется `'9999'` (по умолчанию) либо `'0000'`, если в конфигурации группы задан флаг `emptyFirst: true` (например, для обычных штангенциркулей без твердосплавных накладок, чтобы они отображались перед твердосплавными). Отключенные группы всегда получают `'9999'`.
- **Tie-Breaker (разрешение споров):** в конец ключа добавляется `LPAD(p.id, 6, '0')` (6 символов, архитектурный диапазон ID 110001–350009). При абсолютно одинаковых характеристиках гарантируется стабильный детерминированный порядок по ID.
- **Итоговая длина ключа:** ровно **51 символ** ($9 \times 4 + 9 \text{ разделителей} + 6 = 51$), что гарантирует идеальное лексикографическое сравнение строк в MySQL.

### Пример:
Для микрометра МК (`category_id = 15`): тип order=10, диапазон 0-25 (order=5), точность 0.01 (order=10), бренд ЧИЗ (order=1), ID 110005:
```text
0010_9999_0005_9999_0010_9999_9999_0001_9999_110005
```

## 3. Требования к реализации

### 3.1. Изменения схемы БД
1. Колонка `sort_key VARCHAR(64) NOT NULL DEFAULT ''` в таблице `i_products`.
2. Индекс `idx_cat_sort (category_id, sort_key)` для быстрого чтения страниц категорий.
3. Миграционный скрипт, вычисляющий и проставляющий `sort_key` для всех существующих товаров (1 331 товар).

### 3.2. Серверная утилита генерации ключа
Модуль `server/utils/productSortKey.js`:
- Функция `buildProductSortKey(product, propsOrderingMap)`:
  - Принимает объект товара (обязательно содержит `id`, `category_id`, `p0_brand` ... `p8_pack`).
  - Принимает справочник весов `propsOrderingMap` (`Map<propId, ordering>`).
  - Получает группы из `usePrpsGroupsMap(product.category_id)`.
  - Упорядочивает группы по `(group.sortOrdering ?? group.ordering) ASC`, отправляя `disabled: true` в конец.
  - Формирует и возвращает 51-символьную строку `sort_key`.
- Функция `recalculateProductsSortKey(productIds | { categoryId, propId })`:
  - Загружает полные записи товаров из `i_products` (для предотвращения потери неуказанных свойств при частичных апдейтах).
  - Загружает актуальные `ordering` из `i_properties`.
  - Формирует `sort_key` и выполняет пакетный `UPDATE i_products SET sort_key = CASE id ...`.

### 3.3. Триггеры обновления `sort_key` при изменении данных
Поле `sort_key` автоматически пересчитывается:
1. **Редактирование товара в админке (`server/api/admin/cms/products/updProds.js`):**
   - Выполняется стандартный `UPDATE` пришедших полей.
   - Если среди обновленных полей были `category_id` или `p0_brand`..`p8_pack`, собираются `id` затронутых товаров и вызывается `await recalculateProductsSortKey(updatedIds)`.
2. **Импорт товаров (`server/api/admin/dbImport/products.js`):**
   - При создании/перезаписи товаров вычисляется `sort_key` перед вставкой.
3. **Обновление порядка свойств из админки (`server/api/admin/setProperties.js`):**
   - Если администратор изменил поле `ordering` свойств в таблице `i_properties`:
   - В конце запроса (после применения всей пачки изменений) собираются все измененные `prop.id`, находятся затронутые товары (`WHERE p0_brand IN (...) OR p1_type IN (...) ...`) и вызывается пакетный пересчет `recalculateProductsSortKey(affectedProductIds)`.

### 3.4. Рефакторинг существующих мест сортировки
Переход на `ORDER BY sort_key ASC`:
1. `server/api/getData/category/[c_alias].js`:
   - В SQL-запросе: добавить `ORDER BY sort_key ASC`.
   - Сохранить строки 80–96 (формирование массива `filter` для UI-фильтров каталога).
   - Удалить ручной цикл сортировки товаров (строки 98–108: `products.sort(...)`).
2. `server/api/admin/cms/products/getProds.js`:
   - Добавить `ORDER BY sort_key ASC` в оба SQL-запроса (для корневых категорий и подкатегорий).
3. `app/pages/admin/cms/products.vue`:
   - Удалить клиентскую функцию `sortProdsByProperties` (строки 270–295) — товары с сервера будут приходить уже упорядоченными.
4. `server/api/excel/get-products.get.js`:
   - В SQL-запросе заменить `ORDER BY p.id ASC` на:
     ```sql
     JOIN i_categories c ON c.id = p.category_id
     ORDER BY c.ordering ASC, p.sort_key ASC
     ```
   - Товары в Excel структурируются по порядку категорий каталога и размерным рядам ГОСТ.
5. `server/api/ai/productsData/[c_alias].js`:
   - Удалить дублирующий блок сортировки (строки 211–255), в запрос добавить `ORDER BY sort_key ASC`.
6. `server/api/admin/cms/documentation/getProds.js`:
   - Удалить дублирующий блок сортировки и сборки временных фильтров (строки 44–95), в SQL добавить `ORDER BY sort_key ASC`.

## 4. Критерии приемки (Definition of Done)
1. В таблице `i_products` присутствует колонка `sort_key VARCHAR(64)` с индексом `idx_cat_sort (category_id, sort_key)`.
2. 100% опубликованных товаров имеют корректно рассчитанный 51-значный `sort_key`.
3. Порядок товаров на странице категории идентичен ГОСТ-каталогу без запуска `products.sort` в Node.js.
4. Фильтры каталога на страницах категорий продолжают работать штатно (массив `filter` сохранен).
5. В админке при изменении характеристик товара или порядка свойств `sort_key` обновляется корректно и без потери свойств.
6. В Excel товары отдаются упорядоченными по категориям каталога и характеристикам.
7. После локального тестирования миграция схемы и ключей успешно применена на боевой облачной БД (Beget).
